# Теория к защите ЛР2: процессы и каналы

## 1. Процесс

**Процесс** — это программа в момент выполнения. У процесса есть:

- **PID** — уникальный номер (`getpid()`);
- **PPID** — номер родителя (`getppid()`);
- своё **адресное пространство**: код, данные, куча, стек;
- **таблица файловых дескрипторов**;
- состояние: выполняется, спит (ждёт `read`, например), остановлен, зомби.

Процессы **изолированы**: один процесс не может прочитать память другого. Обмениваться данными они могут только через ядро. Такие механизмы называются **IPC** (межпроцессное взаимодействие): каналы (pipe), сигналы, файлы, сокеты, разделяемая память, очереди сообщений.

## 2. Файловые дескрипторы

Дескриптор — это просто **целое число**, номер строки в таблице открытых файлов процесса. За номером может стоять файл, терминал, канал или сокет. `read` и `write` работают со всеми одинаково.

| fd | Имя | Обычно |
|---|---|---|
| 0 | `STDIN_FILENO` | клавиатура |
| 1 | `STDOUT_FILENO` | терминал |
| 2 | `STDERR_FILENO` | терминал |

Новый дескриптор всегда получает **наименьший свободный номер**. Поэтому в strace первые каналы получают номера 3, 4, 5, 6.

## 3. fork — создание процесса

В Unix новый процесс создаётся **только копированием существующего**. Все процессы, кроме первого (`systemd`, PID 1, его запускает ядро), получены через `fork`:

```
bash
 └─ fork() → копия bash ─ exec("./parent") → parent
                            └─ fork() → копия parent ─ exec("./child") → child
```

После `fork` работают **два** процесса, и оба продолжают выполнение со следующей строки. Отличить их можно по возвращаемому значению:

| Возврат | Кто это |
|---|---|
| `0` | ребёнок |
| `> 0` | родитель (число равно PID ребёнка) |
| `-1` | ошибка, ребёнок не создан |

**Что ребёнок наследует:** копию памяти, копию таблицы дескрипторов (они указывают на **те же** открытые файлы и каналы), обработчики сигналов, текущую директорию, переменные окружения.

**Чем ребёнок отличается от родителя:** у него свой PID, PPID равен PID родителя, своя память (изменения в ребёнке не видны родителю).

**Copy-on-write.** Память при `fork` реально не копируется. Оба процесса смотрят на одни и те же страницы, а копия страницы делается только при записи в неё. Поэтому `fork` + `exec` выполняются быстро.

## 4. exec — замена программы

`execl("./child", "child", filename, NULL)` **заменяет** код, данные и стек текущего процесса новой программой.

- PID **не меняется**.
- Открытые дескрипторы **сохраняются** (кроме помеченных `O_CLOEXEC`). Поэтому перенаправление stdin/stdout продолжает работать.
- При успехе `exec` **не возвращается никогда**, и строка после него выполняется только при ошибке. Поэтому сразу после `execl` стоит `die("execl")`.

Аргументы: путь к программе, `argv[0]`, `argv[1]`, …, `NULL`.

Семейство exec: `l` — аргументы списком, `v` — массивом, `p` — искать программу в `PATH`, `e` — передать своё окружение (`execl`, `execv`, `execlp`, `execvp`, `execve`). Настоящий системный вызов здесь один, `execve`, остальные — обёртки glibc.

**Зачем fork и exec — два отдельных шага?** Между ними ребёнок выполняет ещё наш код и может настроить окружение: перенаправить stdin/stdout через `dup2`, закрыть лишнее, сменить директорию. В лабе именно там каналы подключаются к stdin/stdout ребёнка.

## 5. pipe — канал

`pipe(fd)` создаёт **буфер в памяти ядра** (обычно 64 КБ) и возвращает два дескриптора:

- `fd[0]` — конец для чтения;
- `fd[1]` — конец для записи.

```
 write(fd[1]) → │ ядро: [1][0][0][ ][5]... │ → read(fd[0])
```

Свойства:

- **Однонаправленный.** Для двусторонней связи нужны два канала (pipe1 и pipe2).
- **Анонимный.** Имени в файловой системе у него нет, поэтому доступен только родственным процессам, унаследовавшим дескрипторы через `fork`. Отсюда правило: `pipe` вызывается **до** `fork`.
- **`read` из пустого канала блокирует** процесс, пока не появятся данные.
- **`read` возвращает 0 (EOF)**, только когда закрыты **все** концы записи во всех процессах.
- **`write` в полный канал блокирует** процесс, пока читатель не освободит место.
- **`write` в канал без читателей** вызывает сигнал `SIGPIPE` (по умолчанию он убивает процесс). Если сигнал игнорировать, `write` вернёт -1 с ошибкой `EPIPE`.
- **Границ сообщений нет**, это поток байтов. Строки различаются только по `\n`.
- Запись до `PIPE_BUF` (4096 байт) **атомарна**: она не перемешается с записями других процессов.

**Почему нужно закрывать лишние концы.** Если у parent останется открытым `p2[1]`, то после смерти child в канал всё ещё «может кто-то написать» (сам parent). Тогда `read(p2[0])` никогда не вернёт 0, и parent зависнет навсегда. Та же логика для `p1[0]`.

**Именованный канал (FIFO)** создаётся через `mkfifo`. У него есть имя в файловой системе, поэтому через него могут общаться и неродственные процессы.

## 6. dup2 — перенаправление

`dup2(old, new)` делает `new` копией `old`. Если `new` был открыт, он сначала закрывается.

```c
dup2(p1[0], STDIN_FILENO);   // fd 0 теперь pipe1
dup2(p2[1], STDOUT_FILENO);  // fd 1 теперь pipe2
close(p1[0]); close(p2[1]);  // оригиналы больше не нужны
```

После этого программа `child` читает stdin и пишет stdout и **не знает**, что это каналы. Точно так же shell реализует `cmd1 | cmd2` и `cmd > file`.

## 7. Схема лабы (вариант 3)

```
пользователь → parent ─write(p1[1])→ [pipe1] → stdin  child → файл
                 ↑                                      │
                 └──read(p2[0])── [pipe2] ← stdout ─────┘
```

Шаги:

1. `pipe(p1)`, `pipe(p2)`.
2. `fork()`. Ребёнок получает все 4 дескриптора.
3. Ребёнок: `dup2` ×2, `close` ×4, `execl("./child", ...)`.
4. Parent: закрывает `p1[0]` и `p2[1]`.
5. Цикл: parent пишет строку → child читает, считает, пишет в файл, отвечает 1 байтом (`O`/`E`/`Z`) → parent читает ответ.
6. По `Z` или Ctrl+D parent закрывает `p1[1]` (child получает EOF), закрывает `p2[0]` и вызывает `waitpid`.

## 8. Завершение процесса, wait, зомби, сироты

- `exit(code)` / `return` из `main` завершают процесс. Ядро закрывает все его дескрипторы.
- **Зомби** — процесс, который завершился, но родитель ещё не забрал его код возврата через `wait`/`waitpid`. Ресурсов он почти не занимает, но держит запись в таблице процессов. В `ps` у него статус `Z` / `<defunct>`.
- **Сирота** — процесс, родитель которого умер раньше него. Его «усыновляет» `init`/`systemd` (или subreaper), который потом сам вызывает `wait`.
- `waitpid(pid, &status, 0)` блокирует процесс, пока ребёнок не завершится, и забирает его статус:
  - `WIFEXITED(status)` — завершился нормально;
  - `WEXITSTATUS(status)` — код возврата;
  - `WIFSIGNALED(status)` / `WTERMSIG(status)` — убит сигналом и каким именно.

## 9. Сигналы (кратко)

Сигнал — асинхронное уведомление процесса от ядра или другого процесса.

| Сигнал | Когда приходит |
|---|---|
| `SIGPIPE` | запись в канал без читателей |
| `SIGCHLD` | ребёнок завершился (родителю) |
| `SIGINT` | Ctrl+C |
| `SIGFPE` | арифметическая ошибка (`INT_MIN / -1`, деление на 0 в int) |
| `SIGKILL` | убийство, перехватить нельзя |
| `SIGSEGV` | обращение к чужой памяти |

`signal(SIGPIPE, SIG_IGN)` в parent нужен, чтобы при неожиданной смерти child parent не умер сам, а получил ошибку `write` и корректно завершился.

## 10. Буферизация: почему `write`, а не `printf`

`printf` пишет в буфер stdio. Если stdout — терминал, буфер сбрасывается по `\n`. Если stdout — канал или файл, буфер сбрасывается только при заполнении (~4 КБ) или при выходе. Если бы child отвечал через `printf`, ответ застрял бы в буфере, parent ждал бы его в `read`, а child ждал бы следующую строку. Получилась бы **взаимная блокировка (deadlock)**. `write` — системный вызов без буфера, данные сразу попадают в канал.

Отсюда же видно, почему при `printf ... | ./parent` сообщения в терминале идут в «странном» порядке: stdout parent тоже буферизуется, а stderr — нет.

## 11. Системные вызовы и strace

**Системный вызов** — обращение программы к ядру (переход из пользовательского режима в режим ядра). `fork`, `pipe`, `read`, `write`, `open`, `dup2`, `execve` — системные вызовы. `printf`, `getline`, `strtol` — функции библиотеки (часть из них внутри вызывает `read`/`write`).

```
strace -f -e trace=pipe2,clone,dup2,execve,openat,read,write,close,wait4 ./parent
```

`-f` — следить и за дочерними процессами. Имена в strace отличаются от кода, потому что glibc использует более новые вызовы:

| В коде | В strace |
|---|---|
| `fork` | `clone` |
| `pipe` | `pipe2` |
| `open` | `openat` |
| `waitpid` | `wait4` |

## 12. Обработка ошибок

Каждый системный вызов при ошибке возвращает `-1` и записывает код ошибки в `errno`. `perror("msg")` печатает `msg: <текст ошибки>`. В лабе это делает `die()`: `perror` + `exit(1)`.

Типичные ошибки: `ENOENT` — нет файла, `EACCES` — нет прав, `EPIPE` — канал без читателей, `EMFILE` — слишком много открытых fd, `EAGAIN` — превышен лимит процессов при `fork`.

## 13. Частые вопросы на защите

**Зачем нужен fork?**
Это единственный способ создать процесс. Копирование нужно, чтобы ребёнок унаследовал каналы и успел перенаправить stdin/stdout до `exec`.

**Что вернёт fork и кому?**
Ребёнку 0, родителю PID ребёнка, -1 при ошибке.

**Что будет, если вызвать pipe после fork?**
У каждого процесса будет свой отдельный канал, и связи между ними не будет.

**Что будет, если не закрыть p2[1] в parent?**
После смерти child `read` не вернёт EOF, и parent зависнет.

**Что будет, если не вызвать waitpid?**
Child останется зомби, пока parent жив.

**Сколько раз выполнится printf после двух fork подряд?**
4 раза: после каждого `fork` число процессов удваивается.

**Что произойдёт после успешного exec?**
Старый код исчезнет, а строка после `execl` не выполнится.

**Как child узнаёт, что ввод закончен?**
`getline` вернёт -1 (EOF), когда parent закроет `p1[1]`.

**Как parent узнаёт о делении на 0?**
Child присылает байт `Z` в pipe2.

**Зачем `long` в divide_line?**
`INT_MIN / -1` не помещается в int и вызывает SIGFPE.

**Чем процесс отличается от потока?**
Потоки одного процесса делят общую память и дескрипторы, а процессы изолированы.

**Чем pipe отличается от FIFO?**
FIFO имеет имя в файловой системе и подходит для неродственных процессов.

**Почему stderr child виден в терминале?**
Его не перенаправляли, он унаследован от parent и указывает на терминал.

## 14. Полезные команды

```
make && ./parent          # сборка и запуск
pstree -p | grep parent   # дерево процессов во время работы
ps aux | grep defunct     # проверка на зомби
ls -l /proc/<PID>/fd      # куда смотрят дескрипторы процесса (видно pipe:[...])
strace -f ./parent        # системные вызовы
```
